# RFC 9457 Problem Details Migration Guide

**Applies to:** JFrame 1.8.0

All error responses now follow RFC 9457 Problem Details format (`application/problem+json`). The old proprietary JSON shape is removed. Both Spring and Quarkus produce identical bodies.

---

## What changed

### Error response body shape

| Old field | New field | Notes |
|-----------|-----------|-------|
| `statusCode` | `status` | HTTP status code |
| `errorReason` | `detail` | Human-readable error message |
| `uri` | `instance` | Request path (without query) |
| `method` | *removed* | Not part of RFC 9457 |
| `query` | *removed* | Not part of RFC 9457 |
| `contentType` | *removed* | Not part of RFC 9457 |
| `cause` | *removed* | Security: no internal details on 5xx |
| — | `type` | **New**: stable URI unique per error code |
| — | `title` | **New**: HTTP reason phrase (e.g. "Not Found") |
| `errorCode` | `errorCode` | **Now an extension member** (top-level in JSON) |
| `txId` | `txId` | **Now an extension member** |
| `traceId` | `traceId` | **Now an extension member** |
| `spanId` | `spanId` | **Now an extension member** |

### Content type

- **Old:** `application/json`
- **New:** `application/problem+json`

### Example

**Before (1.7.x):**
```json
{
  "statusCode": 404,
  "errorCode": "USER_001",
  "errorReason": "User does not exist",
  "cause": null,
  "method": "GET",
  "uri": "/api/users/42",
  "query": null,
  "contentType": "application/json",
  "txId": "abc-123",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "spanId": "00f067aa0ba902b7"
}
```

**After (1.8.0):**
```json
{
  "title": "Not Found",
  "status": 404,
  "detail": "User does not exist",
  "instance": "/api/users/42",
  "errorCode": "USER_001",
  "txId": "abc-123",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "spanId": "00f067aa0ba902b7"
}
```

**Note:** `type` is omitted unless `jframe.exception.type-base-uri` is configured. When configured, `type` is built from the base URI plus the percent-encoded error code (RFC 9457: absent `type` means `about:blank`, indicating no semantics beyond the HTTP status).

## Extension members

JFrame adds these top-level fields to Problem Details:

| Field | Type | When present | Example |
|-------|------|--------------|---------|
| `errorCode` | String | Always | `"USER_001"` |
| `txId` | String | When transaction ID is known | `"abc-123"` |
| `traceId` | String | When OTLP tracing is active | `"4bf92f3577b34da6a3ce929d0e0e4736"` |
| `spanId` | String | When OTLP tracing is active | `"00f067aa0ba902b7"` |
| `errors` | Array | Validation errors (400) | `[{"field": "email", "code": "invalid_email"}]` |
| `limit` | Integer | Rate limit exceeded (429) | `100` |
| `remaining` | Integer | Rate limit exceeded (429) | `0` |
| `resetDate` | String (ISO-8601) | Rate limit exceeded (429) | `"2026-10-09T15:30:00Z"` |
| `sortableFields` | Array | Invalid sort (400), always present (`[]` when none) | `["name", "createdAt"]` |
| `searchableFields` | Array | Invalid search (400) | `["name", "description"]` |
| `rejectedParameter` | String | Invalid page (400) | `"size"` |
| `rejectedValue` | int | Invalid page (400) | `-1` |

Absent fields are omitted from the JSON (never sent as `null`). `addExtension()` ignores null values and any name matching a standard member (type, title, status, detail, instance, errorCode, txId, traceId, spanId) or subclass field.

---

## Type URI scheme

The `type` field is **omitted by default**. When `jframe.exception.type-base-uri` is configured, `type` is a stable URI built from:
1. The configured base URI
2. The error code, percent-encoded

**Examples (when base URI is set):**
- Base: `https://myapp.example.com/errors/`; error code `USER_001` → `https://myapp.example.com/errors/USER_001`
- Base: `https://myapp.example.com/errors/`; error code `AUTH/EXPIRED` → `https://myapp.example.com/errors/AUTH%2FEXPIRED`

**RFC 9457 semantics:** Absent `type` means `about:blank`, indicating no semantics beyond the HTTP status. jFrame does not own your application's error-code namespace, so there is no default base URI. Set `jframe.exception.type-base-uri` to point to your own error documentation.

For non-jFrame errors (e.g., Spring MVC exceptions), `errorCode` defaults to the HTTP status name (e.g., `NOT_FOUND` for 404).

On 5xx errors, `errorCode` is always `INTERNAL_SERVER_ERROR` and `detail` is a generic message (never the exception class name or message).

**Title field:** For standard HTTP status codes (e.g. 404), `title` is the reason phrase (e.g. "Not Found"). For non-standard codes (e.g. 599), `title` is a human-readable family label (e.g. "Server Error"; "Unknown Status" outside 1xx–5xx).

---

## Configuration

Two new properties under `jframe.exception.*`:

| Property | Default | Description |
|----------|---------|-------------|
| `jframe.exception.enabled` | `true` | Enable/disable jFrame's global exception handler, enrichers, and OpenAPI error docs. When `false`, jFrame's error handling is off but the rest of jFrame (logging, Jackson, search, OTLP) still works. |
| `jframe.exception.type-base-uri` | *(omitted)* | Base URI for the `type` field. When absent, `type` is omitted from responses (RFC 9457 semantics: `about:blank`). Set this to point to your own error documentation. |

## Step 1: Update error response consumers

Check any code that reads error responses (tests, client libraries, monitoring).

### Client code

**Before:**
```java
if (response.getStatusCode() == 404) {
    String errorCode = response.getBody().get("errorCode");
    String reason = response.getBody().get("errorReason");
}
```

**After:**
```java
if (response.getStatusCode() == 404) {
    String errorCode = response.getBody().get("errorCode");
    String detail = response.getBody().get("detail");  // was errorReason
}
```

**Key changes:**
- Check `status` instead of `statusCode`
- Read `detail` instead of `errorReason`
- Read `instance` instead of `uri`
- `errorCode` is still present (extension member)
- `cause`, `method`, `query`, `contentType` are gone

### Test assertions

Update test matchers to expect Problem Details shape:

**Before:**
```java
assertThat(response)
    .hasStatusCode(404)
    .hasErrorCode("USER_001")
    .hasErrorReason("User does not exist");
```

**After:**
```java
assertThat(response)
    .hasStatus(404)
    .hasErrorCode("USER_001")
    .hasDetail("User does not exist");
```

## Step 2: Update custom enrichers (Spring)

Enrichers no longer use `@Component` — they are registered as `@Bean` methods in your configuration.

### Before (1.7.x)

```java
@Component
public class TenantEnricher implements ErrorResponseEnricher {
    @Override
    public void doEnrich(ErrorResponseResource resource, Throwable throwable,
                         WebRequest request, int statusCode) {
        String tenantId = request.getHeader("X-Tenant-ID");
        if (tenantId != null) {
            resource.addExtension("tenantId", tenantId);
        }
    }
}
```

### After (1.8.0)

```java
@Configuration
public class ErrorHandlingConfig {
    @Bean
    public ErrorResponseEnricher tenantEnricher() {
        return (resource, throwable, request, httpStatus) -> {
            String tenantId = request.getHeader("X-Tenant-ID");
            if (tenantId != null) {
                resource.addExtension("tenantId", tenantId);
            }
        };
    }
}
```

**Changes:**
- Remove `@Component` from enricher classes
- Register enrichers as `@Bean` methods in a `@Configuration` class
- Enricher signature now takes `HttpStatus` (not `int statusCode`)
- Use `addExtension(String, Object)` to add custom fields (replaces direct field setters)

### Enricher ordering

Enrichers run in a deterministic order:

1. **Built-in enrichers** (jFrame's own): `@Order(ErrorResponseEnricher.BUILT_IN_ORDER)` (Spring) or `@Priority(ErrorResponseEnricher.BUILT_IN_PRIORITY)` (Quarkus)
2. **Application enrichers** without `@Order`/`@Priority`: run after built-ins
3. **Application enrichers with explicit order**: sorted by order value

To run your enricher before built-ins, use a lower order value:

```java
@Bean
@Order(ErrorResponseEnricher.BUILT_IN_ORDER - 100)  // runs before built-ins
public ErrorResponseEnricher myEarlyEnricher() { ... }
```

## Step 3: Update custom enrichers (Quarkus)

Enrichers are now registered as CDI beans with `@Priority` for ordering.

### Before (1.7.x)

```java
@ApplicationScoped
public class TenantEnricher implements ErrorResponseEnricher {
    @Override
    public void doEnrich(ErrorResponseResource resource, Throwable throwable,
                         ContainerRequestContext requestContext, int statusCode) {
        String tenantId = requestContext.getHeaderString("X-Tenant-ID");
        if (tenantId != null) {
            resource.addExtension("tenantId", tenantId);
        }
    }
}
```

### After (1.8.0)

```java
@ApplicationScoped
@Priority(ErrorResponseEnricher.BUILT_IN_PRIORITY + 100)  // after built-ins
public class TenantEnricher implements ErrorResponseEnricher {
    @Override
    public void doEnrich(ErrorResponseResource resource, Throwable throwable,
                         ContainerRequestContext requestContext, int statusCode) {
        String tenantId = requestContext.getHeaderString("X-Tenant-ID");
        if (tenantId != null) {
            resource.addExtension("tenantId", tenantId);
        }
    }
}
```

**Changes:**
- Keep `@ApplicationScoped`
- Add `@Priority` for ordering (lower = earlier)
- Use `addExtension(String, Object)` to add custom fields

## Step 4: Disable error handling (optional)

To switch off jFrame's error handling and use your own:

```yaml
# application.yml (Spring)
jframe:
  exception:
    enabled: false
```

```properties
# application.properties (Quarkus)
jframe.exception.enabled=false
```

When disabled:
- Global exception handler is not registered
- Enrichers are not active
- OpenAPI error documentation is not added
- The rest of jFrame (logging, Jackson, search, OTLP) still works

## Step 5: Handle specific exceptions yourself (Spring only)

jFrame's handler now runs last (`@Order(Ordered.LOWEST_PRECEDENCE)`). In 1.7.x it ran first and caught everything, so application handlers were never reached. Your own `@RestControllerAdvice` now wins for the exceptions it handles, including jFrame `HttpException` subtypes:

```java
@RestControllerAdvice
public class OrderErrorAdvice {

    private final ErrorResponseEntityBuilder builder;

    public OrderErrorAdvice(ErrorResponseEntityBuilder builder) {
        this.builder = builder;
    }

    @ExceptionHandler(DataIntegrityViolationException.class)
    public ResponseEntity<ErrorResponseResource> handle(DataIntegrityViolationException ex, WebRequest request) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
            .contentType(MediaType.APPLICATION_PROBLEM_JSON)
            .body(builder.buildErrorResponseBody(new HttpException(OrderErrors.DUPLICATE_ORDER, ex), HttpStatus.CONFLICT, request));
    }
}
```

Using `ErrorResponseEntityBuilder` keeps the jFrame body shape and enrichers. jFrame handles everything you don't.

To replace jFrame's handler entirely, define your own `JFrameResponseEntityExceptionHandler` bean; jFrame backs off when it detects one.

## Removed classes and methods

| Item | Replacement |
|------|-------------|
| `StatusCodeResponseEnricher` | Removed; `status` and `title` are set by `ProblemDetails.apply()` |
| `RequestInfoResponseEnricher` | Removed; `instance` is set by `ProblemDetails.apply()` |
| `ErrorResponseResource.setStatusCode()` | Removed; use `setStatus()` |
| `ErrorResponseResource.setErrorReason()` | Removed; use `setDetail()` or `setError(ApiError)` |
| `ErrorResponseResource.setCause()` | Removed; `cause` field is gone |
| `ErrorResponseResource.setMethod()` | Removed; `method` field is gone |
| `ErrorResponseResource.setUri()` | Removed; use `setInstance()` instead |
| `ErrorResponseResource.setQuery()` | Removed; `query` field is gone |
| `ErrorResponseResource.setContentType()` | Removed; `contentType` field is gone |

## Validation errors

Validation errors (400) now include an `errors` extension member listing each violation:

```json
{
  "title": "Bad Request",
  "status": 400,
  "detail": "Validation failed",
  "instance": "/api/users",
  "errorCode": "VALIDATION_ERROR",
  "errors": [
    {"field": "email", "code": "invalid_email"},
    {"field": "age", "code": "too_young"}
  ]
}
```

---

## Rate limit errors

Rate limit errors (429) include `limit`, `remaining`, and `resetDate` extension members:

```json
{
  "title": "Too Many Requests",
  "status": 429,
  "detail": "Rate limit exceeded",
  "instance": "/api/users",
  "errorCode": "RATE_LIMIT_EXCEEDED",
  "limit": 100,
  "remaining": 0,
  "resetDate": "2026-10-09T15:30:00Z"
}
```

Rate limit headers (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`) are still set.

---

## Invalid sort / search / page errors

Invalid sort, search, and page inputs now include the rejected field and available options as extension members:

**Invalid sort (400):**
```json
{
  "errorCode": "INVALID_SORT",
  "detail": "Field 'unknown' is not sortable",
  "sortableFields": ["name", "createdAt", "updatedAt"]
}
```

**Invalid search (400):**
```json
{
  "errorCode": "INVALID_SEARCH",
  "detail": "Field 'unknown' is not searchable",
  "searchableFields": ["name", "description"]
}
```

**Invalid page (400):**
```json
{
  "errorCode": "INVALID_PAGE",
  "detail": "Page size must be > 0",
  "rejectedParameter": "size",
  "rejectedValue": -1
}
```

**Note:** `sortableFields` is always present; sent as `[]` when empty.

## Spring MVC framework errors

Spring MVC exceptions (404, 405, 415, etc.) now produce jFrame-shaped Problem Details with `errorCode` and correlation extensions, consistent with jFrame's own exceptions.

**Before:** bare Spring `ProblemDetail` without jFrame enrichment.
**After:** full Problem Details with `errorCode`, `txId`, `traceId`, `spanId`.

---

## Security errors (Spring)

Every Spring Security `AuthenticationException` reaching MVC now returns 401 (1.7.x only handled `BadCredentialsException`; others such as `AuthenticationCredentialsNotFoundException` became 500). `AccessDeniedException` returns 403. The exception message is never exposed:

**401 Unauthorized:**
```json
{
  "title": "Unauthorized",
  "status": 401,
  "detail": "Unauthorized",
  "instance": "/api/login",
  "errorCode": "UNAUTHORIZED"
}
```

**403 Forbidden:**
```json
{
  "title": "Forbidden",
  "status": 403,
  "detail": "Forbidden",
  "instance": "/api/admin",
  "errorCode": "FORBIDDEN"
}
```

---

## Filter-level error writing

`ErrorResponseWriter` now writes Problem Details with the application's JSON mapper and jFrame enrichers:

```java
import io.github.jframe.exception.handler.ErrorResponseWriter;

ErrorResponseWriter.write(request, response, UserErrors.UNAUTHORIZED);
```

The response is `application/problem+json` with all correlation extensions (`txId`, `traceId`, `spanId`).

---

## Unhandled exceptions (5xx)

Unhandled exceptions now return a generic 500 Problem Details:

```json
{
  "title": "Internal Server Error",
  "status": 500,
  "detail": "An unexpected error occurred",
  "instance": "/api/users",
  "errorCode": "INTERNAL_SERVER_ERROR"
}
```

**Security:** no stack trace, exception class name, or internal message appears in the body. The exception is still logged server-side with full details.

---

## Compatibility

jFrame's error bodies are validated against the RFC 9457 Appendix A JSON Schema on both Spring and Quarkus runtimes.

---

## OpenAPI documentation

Error responses in OpenAPI now use `application/problem+json` with Problem Details schemas including jFrame's extension members.

**Spring:** `@ApiResponse` annotations automatically document error responses.
**Quarkus:** `JFrameErrorResponseFilter` adds standard error responses (400, 429, 500) to all operations.

---

## Spring `/error` fallback controller

Spring Boot's `BasicErrorController` is replaced by `JFrameErrorController`, which renders jFrame Problem Details for errors outside MVC (exceptions thrown in filters, `response.sendError`). The `instance` field is set to the original request path. `txId` is included only when one exists (from response header, request header, or thread context); never fabricated.

Disable via `jframe.exception.enabled=false` or define your own `ErrorController` bean — jFrame backs off in both cases.

---

## OpenAPI schema cleanup

`ErrorResponseResource` fields `extensions` and `error` are no longer exposed as schema properties (marked `@JsonIgnore`). Quarkus `JFrameErrorResponseFilter` now documents 400, 401, 403, 404, 429, 500 error responses like Spring.

---

## Known differences between runtimes

### Quarkus Security 401/403

Quarkus Security (401/403) raised by authentication/authorisation filters keep Quarkus's native responses (no jFrame Problem Details body). Custom exception mappers would break authentication challenges (e.g. OIDC code flow redirect, `WWW-Authenticate` header). Workaround: use a Vert.x route failure handler to rewrite the body only, preserving status and headers.

## Quarkus: new exception mappers

- `WebApplicationExceptionMapper`: JAX-RS exceptions (`NotFoundException`, `NotAllowedException`, `NotSupportedException`, ...) keep their own status and headers (e.g. `Allow`). In 1.7.x they fell through to `ThrowableMapper` and became 500.
- `ConstraintViolationExceptionMapper`: bean-validation failures return 400 `VALIDATION_ERROR` with `errors`; return-value violations stay 500. In 1.7.x all became 500.

Wrapped exceptions (e.g. `CompletionException`) are not unwrapped on either runtime and return 500.

---

### "Accept: application/json" clients get 406

If a client sends `Accept: application/json` only, they will receive a 406 Not Acceptable. The error response itself is still valid JSON (Problem Details). Clients should accept `application/problem+json` or use a wildcard `Accept: */*`.

### Custom enrichers not running

Ensure enrichers are registered as `@Bean` (Spring) or `@ApplicationScoped` (Quarkus) and implement `ErrorResponseEnricher`. Check `@Order` / `@Priority` values if ordering matters.

### `type` URI is wrong

Check `jframe.exception.type-base-uri` property. When absent, `type` is omitted (RFC 9457 semantics). Set it to point to your own error documentation.

### Error handling is off

Check `jframe.exception.enabled` property. Default is `true`. If set to `false`, jFrame's handler is not active.
