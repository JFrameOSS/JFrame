# Upgrading to JFrame 1.6.1 — Spring Log Export

**Applies to:** JFrame 1.6.1

A single-change patch release. Relevant only to Spring applications that have opted into telemetry.

---

## 1. Will it still compile?

Yes. No API changes.

---

## 2. Will it still behave the same?

Only if you are on Quarkus, or have not opted into telemetry. One change affects Spring applications that export telemetry.

### 2.1 `jframe.otlp.logs.enabled` now works on Spring

In 1.6.0 the property was inert on Spring. `otel.instrumentation.logback-appender.enabled` was hardcoded `false`, independent of it. The appender is what produces log records, so nothing was ever exported — the property controlled the drain while the tap was welded shut. Setting it to `true` or `false` produced identical behaviour, with no warning.

It is now wired to the property:

```yaml
otel:
  instrumentation:
    logback-appender:
      enabled: ${jframe.otlp.logs.enabled}
```

| Runtime | 1.6.0 | 1.6.1 |
| --- | --- | --- |
| **Spring** | No log records produced or exported, whatever `logs.enabled` was set to | Log records exported when `logs.enabled=true` (the default) |
| **Quarkus** | Already exported (`quarkus.otel.logs.exporter=cdi`) | Unchanged |

**Consequence:** a Spring application that has opted into telemetry (`jframe.otlp.disabled=false`) will start sending log records to the OTLP endpoint after upgrading. If your collector backend only handles traces, those exports will fail and generate error noise.

If you do not want log export, set it explicitly:

```yaml
jframe:
  otlp:
    logs:
      enabled: false
```

This only affects applications that have opted into telemetry. `otel.sdk.disabled` still gates everything, and `jframe.otlp.disabled` defaults to `true`.

Applications that were relying on `logs.enabled=false` in 1.6.0 need no change — that setting now does what it always claimed to.

---

## 3. Why it was missed

`OtlpConfigParityTest` compared the two runtimes' declared defaults, and both declared `logs.enabled=true`. The divergence was in what the property was wired to downstream, which the test did not model.

It now also asserts that an enabled signal has a live path on both runtimes, not just a matching default.

---

## 4. Toolchain

Unchanged from 1.6.0.

---

## Checklist

- [ ] **Spring only:** decide whether you want OTLP log export. If your backend is traces-only, set `jframe.otlp.logs.enabled=false`
- [ ] Check collector capacity and ingest cost if log export is now active — this is new volume that 1.6.0 never sent
- [ ] Quarkus applications: no action
