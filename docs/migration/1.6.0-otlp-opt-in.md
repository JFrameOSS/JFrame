# Upgrading to JFrame 1.6.0 — Telemetry Opt-In and OTLP Hardening

**Applies to:** JFrame 1.6.0

Consolidated upgrade guide for the OTLP changes in 1.6.0. Everything that can affect a running application is here, in the order it is most likely to bite.

---

## 1. Will it still compile?

Yes. There are no removed or renamed API types in this release. All changes are behavioural or configuration-level. Skip to section 2.

---

## 2. Will it still behave the same?

No. Five changes affect runtime behaviour without any compile error. Check each one.

### 2.1 Telemetry is now opt-in — Quarkus only

`OtlpDefaults.DEFAULT_DISABLED` flipped from `false` to `true`. The impact differs per runtime.

| Runtime | Before 1.6.0 | After 1.6.0 | Action required? |
| --- | --- | --- | --- |
| **Quarkus** | `jframe.otlp.disabled=false` shipped in defaults — telemetry **on** | `jframe.otlp.disabled=true` — telemetry **off** | **Yes** — set `jframe.otlp.disabled=false` explicitly if you need telemetry |
| **Spring** | Beans gated on `@ConditionalOnProperty(name="jframe.otlp.disabled", havingValue="false")` with no `matchIfMissing` — telemetry already required an explicit opt-in | Unchanged | No — Spring was already effectively opt-in |

Spring users: the documented default changed in metadata, but no application behaviour changes. Do not chase this.

Quarkus users: an application that relied on telemetry being active by default will go dark after upgrading, with no compile error and no warning at startup. Set the property explicitly:

```properties
# Quarkus — restore telemetry after upgrading
jframe.otlp.disabled=false
```

```yaml
# Spring — no change needed; was already required
jframe:
  otlp:
    disabled: false
```

### 2.2 Process resource attributes excluded by default (security fix)

New property: `jframe.otlp.excluded-resource-attributes`

Default value: `process.command_args, process.command_line, process.executable.path`

**Why:** The JVM command line is captured verbatim by OpenTelemetry's `ProcessResourceProvider`. Any secret passed as a `-D` flag (e.g. `-Dspring.datasource.password=secret`) lands in the resource block of every exported trace. OpenTelemetry Semantic Conventions 1.44.0 (Process resource) classifies these three attributes as **Opt-In** and states they "SHOULD NOT be collected by default unless there is sanitization that excludes sensitive data". Shipping them on by default was the deviation; excluding them is the spec-conformant behaviour.

What is still exported — only the three Opt-In attributes are dropped:

| Attribute | Semconv status | 1.6.0 behaviour |
| --- | --- | --- |
| `process.pid` | Required | Still exported |
| `process.runtime.name` | Recommended | Still exported |
| `process.runtime.version` | Recommended | Still exported |
| `process.runtime.description` | Recommended | Still exported |
| `process.command_args` | **Opt-In** | **Excluded by default** |
| `process.command_line` | **Opt-In** | **Excluded by default** |
| `process.executable.path` | **Opt-In** | **Excluded by default** |

**Implementation note:** the value of `jframe.otlp.excluded-resource-attributes` is forwarded to the SDK as `otel.resource.disabled.keys`. Do not set `quarkus.otel.experimental.resource.disabled-keys` — it is declared in Quarkus's `OTelRuntimeConfig` but is never consumed; it is dead config.

If you genuinely need these attributes, set the property to an empty list — but sanitize your command line first:

```yaml
# Spring — re-enable Opt-In process attributes (sanitize command line before doing this)
jframe:
  otlp:
    excluded-resource-attributes: []
```

```properties
# Quarkus
jframe.otlp.excluded-resource-attributes=
```

Grep to find `-D` flags carrying secrets in your start scripts or Helm values before opting back in:

```bash
grep -rn "\-D.*password\|\-D.*secret\|\-D.*token\|\-D.*key" \
  --include="*.yml" --include="*.yaml" --include="*.sh" --include="*.properties" .
```

### 2.3 `sampling-rate` now actually works on Spring

**This is the change most likely to surprise you in production.**

Previously on Spring, `jframe.otlp.sampling-rate` set the sampler *argument* but never set `otel.traces.sampler`, so the SDK default `parentbased_always_on` won. Every trace was sampled regardless of the configured rate. Setting `sampling-rate: 0.1` silently produced 100% sampling.

New property `jframe.otlp.sampler-type` defaults to `parentbased_traceidratio`, so `sampling-rate` is now honoured.

| | Before 1.6.0 | After 1.6.0 |
| --- | --- | --- |
| Effective sampler (Spring) | `parentbased_always_on` (SDK default) | `parentbased_traceidratio` |
| `sampling-rate: 0.1` effect | 100% sampling (silently ignored) | ~10% sampling (working as intended) |

**Consequence:** anyone who set a low `sampling-rate` as a cost-control measure and never noticed it was inert will see their exported trace volume drop sharply after upgrading. That is the property finally working — not a regression. Anyone who tuned other settings (retention, Collector resources, alerting thresholds) to compensate for the inflated volume should re-check them.

```bash
# Find applications that had a non-default sampling-rate set
grep -rn "sampling-rate" --include="*.yml" --include="*.yaml" --include="*.properties" .
```

### 2.4 Spring now exports OTLP log records

Previously on Spring, `otel.instrumentation.logback-appender.enabled` was hardcoded `false`, independent of `jframe.otlp.logs.enabled`. The appender is what produces log records, so nothing was ever exported — `logs.enabled` controlled the drain while the tap was welded shut. Both `true` and `false` behaved identically, with no warning.

It is now wired to the property:

```yaml
otel:
  instrumentation:
    logback-appender:
      enabled: ${jframe.otlp.logs.enabled}
```

| Runtime | Before 1.6.0 | After 1.6.0 |
| --- | --- | --- |
| **Spring** | No log records produced or exported, whatever `logs.enabled` was set to | Log records exported when `logs.enabled=true` (the default) |
| **Quarkus** | Already exported (`quarkus.otel.logs.exporter=cdi`) | Unchanged |

**Consequence:** a Spring application that has opted into telemetry (`jframe.otlp.disabled=false`) will start sending log records to the OTLP endpoint after upgrading. If your collector backend only handles traces, those exports will fail and generate error noise. Turn log export off explicitly:

```yaml
jframe:
  otlp:
    logs:
      enabled: false
```

This only affects applications that have opted into telemetry — `otel.sdk.disabled` still gates everything, and `jframe.otlp.disabled` defaults to `true`.

### 2.5 Invalid sort columns no longer return 400

`AbstractSortSearchMetaData.toSort()` (and `AbstractPanacheSearchMetaData`) previously threw `IllegalArgumentException("Attempted to sort on non-sortable fields: ...")` when a request asked to sort on an unregistered column. It now discards the invalid columns, keeps the valid ones, and returns `Sort.unsorted()` only when every requested column was invalid. Discarded columns are logged at WARN:

```
WARN "Discarding non-sortable or unregistered sort columns: {}"
```

| Request | Before 1.6.0 | After 1.6.0 |
| --- | --- | --- |
| Sorts on one unknown column, others valid | `IllegalArgumentException` → 400 | WARN log → 200, sorted by the valid columns only |
| Sorts only on unknown columns | `IllegalArgumentException` → 400 | WARN log → 200, `Sort.unsorted()` (default/unspecified order) |

A request that used to fail fast with a client error now succeeds and returns data in an unspecified order. Contract tests or client code asserting on that 400 or the exception message will now break or silently pass wrong data.

```bash
# Find tests asserting on the old exception message
grep -rn "non-sortable fields\|Attempted to sort" --include="*.java" src/
```

Watch the WARN log in production as the signal that a client is sending bad sort parameters.

## 3. New configuration properties

| Property | Default | What it does |
| --- | --- | --- |
| `jframe.otlp.excluded-resource-attributes` | `process.command_args, process.command_line, process.executable.path` | Resource attributes forwarded to `otel.resource.disabled.keys` and excluded from all traces |
| `jframe.otlp.sampler-type` | `parentbased_traceidratio` | Sets `otel.traces.sampler`. Activates the sampler type that makes `sampling-rate` meaningful on Spring |
| `jframe.otlp.traces.enabled` | `true` | When `false`, sets `otel.traces.exporter=none` |
| `jframe.otlp.metrics.enabled` | `true` | When `false`, sets `otel.metrics.exporter=none` |
| `jframe.otlp.logs.enabled` | `true` | When `false`, sets `otel.logs.exporter=none` |

The per-signal toggles (`traces.enabled`, `metrics.enabled`, `logs.enabled`) replace the `OTEL_METRICS_EXPORTER=none` environment-variable workaround previously applied externally (e.g. in Helm charts). Express it as configuration instead:

```yaml
# Spring — traces-only backend (metrics and logs off)
jframe:
  otlp:
    disabled: false
    traces:
      enabled: true
    metrics:
      enabled: false
    logs:
      enabled: false
```

```properties
# Quarkus — traces-only backend (metrics and logs off)
jframe.otlp.disabled=false
jframe.otlp.traces.enabled=true
jframe.otlp.metrics.enabled=false
jframe.otlp.logs.enabled=false
```

## 4. Spring/Quarkus parity

The two runtimes' defaults had silently diverged. The most consequential divergence was `jframe.otlp.disabled`: effectively `true` on Spring (conditional required explicit opt-in), `false` on Quarkus (shipped in defaults). The same configuration block produced telemetry on Quarkus and silence on Spring.

Parity is now verified automatically by `OtlpConfigParityTest` in `jframe-core`. The two runtimes cannot drift again without a build failure.

That test originally compared declared defaults only, which is why it did not catch the log-export gap in 2.4 — both runtimes declared `logs.enabled=true` while only Quarkus had a working path behind it. It now also asserts that an enabled signal has a live path on both runtimes, not just a matching default.

Additional: Quarkus now emits `service.environment` alongside the existing `deployment.environment` resource attribute, matching Spring.

## Checklist

- [ ] **Quarkus only:** set `jframe.otlp.disabled=false` explicitly if your application exports telemetry — it no longer defaults to on
- [ ] Check if you set `sampling-rate` on Spring: if so, expect a sharp drop in exported trace volume — that is correct behaviour. Re-check retention settings, Collector capacity and alerting thresholds calibrated against the old inflated volume
- [ ] Review command-line start scripts and Helm values for `-D` flags carrying secrets; the three Opt-In process attributes are now excluded by default — opt back in only after sanitizing
- [ ] `grep -rn "non-sortable fields\|Attempted to sort" --include="*.java" src/` — update any tests asserting on the old exception or the 400 response
- [ ] **Spring only:** if your backend handles traces but not logs, set `jframe.otlp.logs.enabled=false` — Spring now actually exports log records, where before it silently exported none
- [ ] Replace `OTEL_METRICS_EXPORTER=none` (and equivalent env-var workarounds) in Helm charts or start scripts with `jframe.otlp.metrics.enabled=false`
- [ ] Remove any `quarkus.otel.experimental.resource.disabled-keys` config — it is dead and has no effect
- [ ] Run integration tests with telemetry enabled at least once after upgrading to confirm spans are still exported
