# Upgrading to JFrame 1.6.2 — Deterministic OpenAPI Validation Schema

**Applies to:** JFrame 1.6.2

A single-change patch release. Relevant only to Spring applications that publish an OpenAPI spec via springdoc.

---

## 1. Will it still compile?

Yes. `MethodArgumentNotValidResponseResource` still exists, keeps its constructors and still exposes `getErrors()`/`setErrors()`. It now inherits them from `ValidationErrorResponseResource`.

---

## 2. Will it still behave the same?

At runtime, yes. The JSON body of every 400 response is unchanged.

The generated OpenAPI spec changes once.

### 2.1 One 400 validation schema

In 1.6.1 two handlers in `JFrameResponseEntityExceptionHandler` both declared `responseCode = "400 (Validation)"`, each with a different schema. springdoc keeps one response per code, and which one won depended on JVM reflection order. The spec therefore flipped between builds, randomly showing `ValidationErrorResponseResource` or `MethodArgumentNotValidResponseResource`.

Now only `handleJframeValidation` declares it, and the schema is always `ValidationErrorResponseResource`. Both schemas had the same shape.

| | 1.6.1 | 1.6.2 |
| --- | --- | --- |
| `400 (Validation)` schema | `ValidationErrorResponseResource` **or** `MethodArgumentNotValidResponseResource` (random) | Always `ValidationErrorResponseResource` |
| `MethodArgumentNotValidResponseResource` in `components.schemas` | Sometimes | No longer emitted |
| Response body | Unchanged | Unchanged |

**What to do:**

- **Contract/snapshot tests:** re-baseline once. The diff shows the schema swap on every path; after that it stays stable.
- **Generated clients** (TypeScript, Java, …): if your code references the generated `MethodArgumentNotValidResponseResource` type, switch to `ValidationErrorResponseResource`. The fields are identical.

### 2.2 Custom enrichers

`MethodArgumentNotValidResponseResource` is now a subtype of `ValidationErrorResponseResource`. A custom `ErrorResponseEnricher` that checks `resource instanceof ValidationErrorResponseResource` without also checking the exception type now matches bean-validation errors too. JFrame's own enrichers check the exception type, so they are not affected.

---

## 3. Why it was missed

No test asserted that the `@ApiResponse` codes on the advice are unique. `JFrameResponseEntityExceptionHandlerTest` now checks this.
