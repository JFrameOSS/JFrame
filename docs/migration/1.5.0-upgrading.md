# Upgrading to JFrame 1.5.0

**Applies to:** JFrame 1.5.0

Consolidated upgrade guide. Everything a consuming application needs to check, in the order it is likely to bite.

Detailed background lives in [`1.5.0-filters-opt-in.md`](./1.5.0-filters-opt-in.md) and
[`1.5.0-library-efficiency.md`](./1.5.0-library-efficiency.md). This document is the checklist.

---

## 1. Will it still compile?

Run a build first. These are the only changes that break compilation.

| Change | Symptom | Fix |
| --- | --- | --- |
| `JFrameErrorCode.RATE_LIMITED` renamed to `RATE_LIMIT_EXCEEDED` | `cannot find symbol` | Rename the reference |
| `JFrameErrorCode.INTERNAL_ERROR` renamed to `INTERNAL_SERVER_ERROR` | `cannot find symbol` | Rename the reference |
| `Constants.Headers.TRACE_ID_HEADER` removed | `cannot find symbol` | Use the W3C `traceparent` header, or read the trace id from the OpenTelemetry span |
| `Constants.Headers.SPAN_ID_HEADER` removed | `cannot find symbol` | Same as above |
| `SharedMapperConfig` now registers a `UUID` to `String` mapper | `Ambiguous mapping methods found for mapping property java.util.UUID to java.lang.String` | Delete your own `UUID` to `String` method, or qualify the mapping with `@Mapping(qualifiedByName = ...)` |
| `commons-io` no longer on the compile classpath | `package org.apache.commons.io does not exist` | Declare `commons-io` yourself, or use `InputStream.readAllBytes()` |
| `spring-boot-starter-aop` replaced by `aspectjweaver` | Only if you relied on it arriving transitively | Declare the AspectJ or Spring AOP dependency you actually use. Spring Boot 4 GA no longer publishes the AOP starter |

Grep commands:

```bash
grep -rn "RATE_LIMITED\|INTERNAL_ERROR" --include="*.java" src/
grep -rn "TRACE_ID_HEADER\|SPAN_ID_HEADER" --include="*.java" src/
grep -rn "org.apache.commons.io" --include="*.java" src/
grep -rn "UUID.*String\|String.*UUID" --include="*Mapper.java" src/
```

## 2. Will it still behave the same?

These compile fine and change behaviour silently. Check each one.

### 2.1 Error codes no longer carry the `JFRAME_` prefix

Anything matching on the wire format is affected: client error handling, alerting rules, log queries, contract tests.

| Before | After |
| --- | --- |
| `JFRAME_BAD_REQUEST` | `BAD_REQUEST` |
| `JFRAME_NOT_FOUND` | `NOT_FOUND` |
| `JFRAME_VALIDATION_ERROR` | `VALIDATION_ERROR` |
| `JFRAME_HTTP_ERROR` | `HTTP_ERROR` |
| `JFRAME_RATE_LIMITED` | `RATE_LIMIT_EXCEEDED` |
| `JFRAME_INTERNAL_ERROR` | `INTERNAL_SERVER_ERROR` |

```bash
grep -rn "JFRAME_" --include="*.java" --include="*.ts" --include="*.json" --include="*.yml" .
```

### 2.2 Correlation ID filters are now opt-in

| Filter | Spring | Quarkus | Default in 1.5.0 |
| --- | --- | --- | --- |
| `request-duration` | yes | yes | **on** (logs at DEBUG) |
| `request-response` | yes | yes | **on** (logs at DEBUG) |
| `user-identity` | yes | yes | **on** |
| `request-id` | yes | yes | **off** |
| `transaction-id` | yes | yes | **off** |
| `outbound-correlation` | — | yes | **off** |
| `outbound-logging` | — | yes | **off** |

If your application depends on `x-request-id` or `x-transaction-id` being generated or propagated, turn them back on:

```yaml
# Spring
jframe:
  logging:
    filters:
      request-id:
        enabled: true
      transaction-id:
        enabled: true
```

```properties
# Quarkus
jframe.logging.filters.request-id.enabled=true
jframe.logging.filters.transaction-id.enabled=true
jframe.logging.filters.outbound-correlation.enabled=true
```

`requestId` and `transactionId` in MDC and in error response bodies will be absent until you do.

### 2.3 Request and response logging moved from INFO to DEBUG

The request/response summary lines and the duration line are now logged at DEBUG. Set the logger to DEBUG to get them back:

```yaml
logging:
  level:
    io.github.jframe.logging: DEBUG
```

When DEBUG is off the filter now short-circuits **before** buffering the body, so there is no cost. That also means enabling the filter without enabling DEBUG produces no output at all.

### 2.4 `x-trace-id` and `x-span-id` response headers are gone

`TracingResponseFilter` was deleted in both frameworks. Trace context now travels only via the standard W3C `traceparent` header.

Not affected: `traceId` and `spanId` in **error response bodies** — those come from `TracingResponseEnricher` (Spring) and `TracingEnricher` (Quarkus), which are untouched.

Check any client code, browser tooling or synthetic monitor that reads those response headers.

### 2.5 Duration decimal separator is now always `.`

The logged duration used the JVM default locale, so a European-locale JVM emitted `12,35`. It now always emits `12.35`. Check any dashboard or parser that consumed that field.

### 2.6 Password masking now matches field names containing uppercase letters

The shipped default `fields-to-mask` includes `keyPassphrase`, which previously could never match. It is now redacted. Masking only ever redacts more, never less — but check log-based assertions or fixtures that expected the unmasked value.

### 2.7 Response body logging cap is now actually enforced

`jframe.logging.response-length` was ignored on three of the four Spring logging paths. It is now applied on all of them, at the byte layer before decode and masking. If you set a small cap and relied on seeing full bodies anyway, raise it. Default is `-1` (unlimited).

The application and the downstream client always receive the full body — only the logged copy is bounded.

## 3. OpenTelemetry dependencies (Spring only)

Nothing here breaks compilation. It changes what your build resolves, which is where the real
breakage was.

### 3.1 What changed and why

`jframe-spring-otlp` used to export the OpenTelemetry instrumentation BOM to every consumer. That
BOM manages the same `io.opentelemetry:*` coordinates Spring Boot's own platform manages, so two
platforms competed for one set of versions. Spring Boot won the version, but the instrumentation
jars had been compiled against a newer OpenTelemetry API. The result was a runtime failure with no
build warning:

```
java.lang.NoClassDefFoundError: io/opentelemetry/api/impl/InstrumentationUtil
```

From 1.5.0 the ownership is split and enforced:

| Coordinates | Versioned by |
| --- | --- |
| `io.opentelemetry:*` (api, context, sdk, exporters) | Spring Boot. JFrame never versions these |
| `io.opentelemetry.instrumentation:*` | JFrame, pinned to the release train targeting the API version Spring Boot pins |
| `io.opentelemetry.semconv:*` | JFrame. Not managed by Spring Boot |

A build check (`otelVersionGuard`, bound to `check`) fails the JFrame build if any
`io.opentelemetry` artifact is ever requested at a higher version than the one resolved. A future
Spring Boot upgrade that moves the pinned API version now turns the build red instead of shipping a
silent mismatch.

### 3.2 Remove any BOM workaround you added

If you pinned the instrumentation BOM yourself to work around the failure above, **delete it**.
Keeping it re-creates the same mismatch from the other side.

```kotlin
// DELETE THIS
imports {
    mavenBom("io.opentelemetry.instrumentation:opentelemetry-instrumentation-bom:2.30.0")
}
```

### 3.3 B3, Jaeger and OpenTracing propagation now need an explicit dependency

`opentelemetry-extension-trace-propagators` is no longer pulled in. It only supplies non-W3C
propagation *formats*. W3C `traceparent` and `baggage` are built into `opentelemetry-api` and are
unaffected, so the JFrame default of `otel.propagators: [tracecontext, baggage]` keeps working with
no changes.

You are only affected if you set `otel.propagators` to `b3`, `b3multi`, `jaeger` or `ottrace`:

```kotlin
// no version - Spring Boot's platform supplies it
implementation("io.opentelemetry:opentelemetry-extension-trace-propagators")
```

Note that exporting traces *to* a Jaeger backend does not require this. Modern Jaeger ingests OTLP,
which is configured through `otel.exporter.otlp.*` and is unrelated to propagation format.

## 4. Properties removed

Delete these if present; they no longer do anything.

| Property | Framework | Note |
| --- | --- | --- |
| `jframe.logging.filters.tracing-id.enabled` / `.order` | Spring | Filter deleted |
| `jframe.logging.filters.tracing-response.enabled` | Quarkus | Filter deleted |
| `jframe.otlp.propagators` | Spring | Was never wired to anything. Use `otel.propagators` |

`jframe.otlp.propagators` on **Quarkus** is still live and still mapped to `quarkus.otel.propagators` — leave it alone.

The shipped default propagator list changed from `[b3, jaeger, tracecontext]` to `[tracecontext, baggage]`. If you talk to a service that only speaks B3 or Jaeger, set `otel.propagators` explicitly.

## 5. New functionality available

Nothing here is required. It is what the engineer can start using.

### Utilities

| Type | Module | What it does |
| --- | --- | --- |
| `AmountUtils.normalizeAmount(BigDecimal)` | `jframe-core` | Null-safe. Guarantees a minimum scale of two while preserving any greater scale. `10` becomes `10.00`, `1.500` becomes `1.50`, `1.2345` stays `1.2345`. Never rounds |

### MapStruct mappers

`SharedMapperConfig` now declares `uses = { UuidMapper.class, AmountMapper.class }`. Any mapper annotated `@Mapper(config = SharedMapperConfig.class)` inherits these.

| Mapper | Module | Auto-applies? |
| --- | --- | --- |
| `UuidMapper` | `jframe-spring/core` | **Yes.** `UUID` to `String` converts automatically |
| `AmountMapper` | `jframe-spring/core` | No. Same-type `BigDecimal` conversions are direct assignments; reference it explicitly with `@Mapping(qualifiedByName = "normalizeAmount")` |
| `DateTimeMapper` | `jframe-spring/core` | **No, deliberately.** Three of its four methods assume UTC. Auto-applying `LocalDateTime` to `ZonedDateTime` across a non-UTC estate would silently shift timestamps |

Opting in to `DateTimeMapper` per mapper:

```java
@Mapper(config = SharedMapperConfig.class, uses = DateTimeMapper.class)
public interface OrderMapper {
    OrderDto toDto(Order order);
}
```

Consumer-level `uses` **merges** with the config-level registry rather than replacing it, so both sets of conversions stay available.

`DateTimeMapper.toOffsetDateTime(String)` is now null-safe. It previously threw `NullPointerException`.

### Extension points

| API | Module | Note |
| --- | --- | --- |
| `RequestResponseLogger.isDebugEnabled()` | both | New `default` method returning `true`. Custom implementations keep compiling unchanged. Override it to let the filter skip body buffering when your logger is not going to emit anything |
| `WrappedContentCachingResponse.getContentForLogging()` | `jframe-spring/core` | Returns the size-capped copy. `getContentAsByteArray()` deliberately still returns everything, because `ShallowEtagHeaderFilter` depends on that contract |

### Fixed without action

- **`jframe-spring-jpa` now registers itself.** Previously `DatasourceProxyConfiguration` only activated as a side effect of another module's component scan, so depending on `jframe-spring-jpa` alone silently produced no datasource query logging. Note this is what surfaced the OpenTelemetry conflict in section 3: a proxied `DataSource` bean activates the JDBC instrumentation that was previously dormant.
- **Faster startup.** The broad `io.github.jframe` component scan is gone from both auto-configurations; beans are registered explicitly.
- **Lower per-request cost.** Allocations removed from always-on code paths: filter attribute keys, content-type normalisation, path-exclusion matching, the password masker, `@Traced` annotation lookup, and duration formatting.
- **Published Jackson constraint.** `jframe-spring-core` now publishes a `jackson-annotations:2.22` constraint. If you combine JFrame with springdoc and hit `NoClassDefFoundError: JsonApplyView`, this is the fix — no workaround needed on your side.

## 6. Toolchain

Relevant only if you pin these yourself.

Gradle 9.7.0 · Spring Boot 4.1.0 · Quarkus 3.38.2 · Jackson 3.2.1 · Logback 1.6.3 · JUnit 6.1.3

## 7. Checklist

- [ ] Build. Fix the compile errors in section 1
- [ ] `grep -rn "JFRAME_"` across application code, client code, alerting rules and dashboards
- [ ] Decide whether `request-id` and `transaction-id` need to be re-enabled
- [ ] Set `io.github.jframe.logging` to DEBUG if you want request/response logs
- [ ] Check anything reading the `x-trace-id` or `x-span-id` response headers
- [ ] Check parsers of the logged duration field for the decimal separator
- [ ] Remove the deleted properties from `application.yml` / `application.properties`
- [ ] Remove any `opentelemetry-instrumentation-bom` pin you added as a workaround
- [ ] Add `opentelemetry-extension-trace-propagators` only if you set `otel.propagators` to b3, jaeger or ottrace
- [ ] Run integration tests with logging at DEBUG at least once, to exercise the body-capping paths
